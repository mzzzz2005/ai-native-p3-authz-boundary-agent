# 本地教学文档服务：被测目标

## 为什么需要它

P3 的被测目标不是一个外部系统，而是本项目自己要造出来的东西。没有现成的
「本地教学文档服务」在那里等着接入，所以本仓库自带一个最小实现，跑在
`127.0.0.1` 上。

这样做的价值：授权边界变成真的。`401` 和 `403` 由服务端真实判断并返回，不再是
Fixture 里写死的状态码；撤权意味着服务端真的不再接受那个凭据。

## 服务做了什么

| 项 | 说明 |
| --- | --- |
| 监听地址 | `127.0.0.1`，端口由系统分配，不对外开放 |
| 依赖 | 仅 Python 标准库 |
| 身份 | 三个虚构用户：`A`、`B`、`revoked_A`，各持一个虚构凭据 |
| 资源 | 两份文档 `DA`、`DB` 及各自附件 |
| 接口 | `GET /documents/{doc_id}`、`GET /documents/{doc_id}/attachment` |
| 鉴权 | 缺少或未知凭据返回 `401`；凭据已撤销返回 `401`；越权返回 `403`；允许则 `200` |

凭据与文档正文都是虚构教学数据，只在本机回环地址上有意义，不指向任何真实系统。

## 两份部署配置

授权规则写在部署配置里，服务启动时读取。**测试 Agent 不读这份配置**，它只看
HTTP 响应——这样误配才是真的被"发现"，而不是照着答案念。

| 配置 | 含义 | 用途 |
| --- | --- | --- |
| `config/service.correct.json` | 只有属主可读 | 基线，预期六项全部未确认 |
| `config/service.overpermissive.json` | 文档接口额外放行了 `A` 读 `DB`，附件接口没有 | 已知缺陷，用于验证 Agent 能否找到并只找到它 |

`service.overpermissive.json` 模拟的是一种很常见的真实缺陷：权限检查只加在了
其中一个端点上。正文接口放行了，附件接口没有，所以从外部只能通过对比两个请求的
响应才能发现。

## 运行

```text
python scripts/run_service_scenario.py --deployment correct
python scripts/run_service_scenario.py --deployment overpermissive
```

每次运行都会启动服务、发出六个真实 HTTP 请求、落盘证据、再关闭服务。

## 实测结果

| 部署 | 实际尝试 | 结论 |
| --- | --- | --- |
| `correct` | 6 | 六项全部 `NOT_CONFIRMED`，未覆盖为空 |
| `overpermissive` | 6 | 仅 `T02` 为 `CONFIRMED`，其余五项未确认 |

`overpermissive` 那次能找到 T02，是因为 `A` 拿到了属于 `B` 的文档正文并含教学标记；
T04 仍然返回 `403`，所以没有被误报。这正好检验了 Agent 会不会过度报告。

## 边界

- 服务只在回环地址监听，不接收外部连接，不接触真实数据。
- Agent 侧的客户端没有任何"任意 URL"入口：每个注册检查对应固定的方法与路径，
  凭据由受信宿主按身份引用注入。
- 非本机地址或未注册检查会被客户端直接拒绝，不会发出请求。
- 这是教学用虚构服务，不能作为真实系统的安全结论。
